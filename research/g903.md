# Logitech G903 LIGHTSPEED (HERO)

Findings for the G903, gathered to add a second device type to Loginux.
Labels follow [README.md](README.md#evidence-labels). The writes so far
were RAM-only lighting requests and, in one test, the onboard-mode switch;
each was handed back, and the mouse read back its earlier state.

## Identity (live, 2026-10-22)

- **On its cable:** USB `046d:c091`, named "G903 LIGHTSPEED Wireless Gaming
  Mouse w/ HERO". Interface 0 carries the mouse reports and interface 1 the
  keyboard reports used for macros. Interface 2 carries HID++ (vendor usage
  page `ff00`) and nothing else, so access to it exposes no input.
- **Through its LIGHTSPEED receiver** (`046d:c539`): the Linux DJ driver
  shows the mouse as `046d:4087` "G903 LS", in slot 1 (`HID_PHYS` ends in
  `:1`). That node also carries the mouse's movement and button reports.
- HID++ 4.2 in both connections. `0x8071` is version 0, the first version of
  the feature; the G316 has version 5.

## Lighting

Two `0x8071` clusters, four effects each, and no `0x8081` per-key lighting.
The byte columns are the cluster's `getInfo` reply, read with
`loginux probe`. (live; the column meanings are static, from the `0x8071`
specification)

| Cluster | Location | Effects (index: ID) | Display persistency (byte 5) | LED patterns (byte 7) |
| --- | --- | --- | --- | --- |
| 0 | `0x0001` primary | 0: off, 1: Static `0x01`, 2: Cycle `0x03`, 3: Breathe `0x0a` | `07` | `00` |
| 1 | `0x0002` logo | the same four | `00` | `00` |

- **Cluster 0 is the DPI indicator.** The G903 manual names two lighting
  zones, "DPI indicators" and "G logo". The DPI indicators are three LEDs
  under the DPI buttons. They show the DPI level or onboard profile, and
  for seven seconds after power-on the battery level, by how many bars are
  lit and in which colour. (static, Logitech's G903 setup guide and support
  pages) Cluster 1 is the logo (live), so cluster 0 is the indicator.
  (inference)
- **Its firmware decides which LEDs are on.** The specification describes a
  cluster of several LEDs on one RGB driver, with the DPI LEDs as its
  example. Byte 5 lists the modes the cluster's event display supports.
  Cluster 0 reports `07`: always on, always off, and on for a while after
  each event. Byte 7 says whether a host may choose which LEDs are on, with
  function 2 `setMultiLedRgbClusterPattern`, and cluster 0 reports `00`, so
  a host cannot. (live bytes; meanings static)
- **Non-volatile settings**, read with `manageNvConfig` in its get form
  (function 3, `[00 capability]`): the device lists boot-up effect, demo and
  events display. The boot-up effect is enabled, demo mode is off, and the
  events display is `01`, always on, with a 7-second timeout parameter.
  (live)
- `0x8100` onboard profiles reads mode `01`, onboard. (live)

## What host control shows (live, 2026-10-22)

Six watched tests, 10 seconds each, every one handed back with software
control `00 00` read back afterwards. All six asked for a colour or effect on
both clusters:

| Test | What changed from test 1 | Logo | DPI LEDs |
| --- | --- | --- | --- |
| 1 | claim `01 00`, Static: logo red, cluster 0 blue | red | off |
| 2 | each cluster painted twice | red | off |
| 3 | cluster 0 Static also sent for power modes 1 and 2 (persistence `05`, `09`) | red | off |
| 4 | claim `03 04`, as Solaar claims | red | off |
| 5 | Cycle effect on cluster 0 | red | off |
| 6 | onboard mode switched to host (`02`) before the claim and back to `01` after; run twice | red | off |

Why no variant could work: claiming software control "disables all FW RGB
clusters handling" (specification). On this mouse that handling also
decides which DPI LEDs are on, and the host has no call to switch them on.
The host sets a colour on LEDs that the firmware keeps off. The logo is one
LED with no event display, so it shows what the host sets. (inference from
the bytes and the six results)

## Open questions

- **Events under host control.** Do the DPI LEDs light when the DPI button
  is pressed while a host holds software control, and in the host's colour
  or the firmware's? One watched check answers it: claim, set cluster 0 to
  one colour, press DPI up and then DPI down.
- **How G HUB does it** (planned). A USB capture of G HUB on Windows, like
  the G316 capture, would show whether G HUB lights the DPI LEDs at all, and
  if so whether through `0x8071` or by writing the lighting into the onboard
  profiles. Changing an onboard profile writes the mouse's flash; libratbag
  drives `0x8071` mice only that way. (static, libratbag `driver-hidpp20.c`)

## Loginux support

- `devices/g903-hero.toml` lists the logo (cluster 1) only. Loginux sets it
  to Static, Cycle or Breathe in RAM, after the claim `01 00`. Loginux never
  writes cluster 0, but its claim takes every cluster, so the DPI indicator
  stays dark while Loginux holds the lighting.
- With Claude Code's status display on, the logo shows the first running
  instance's state: each frame that changes it goes out as a new Static
  colour, up to 12.5 a second. This has run only against the simulated mouse
  of the tests.
- Access: `udev/70-loginux.rules` gives the session interface 2 of
  `046d:c091` only.
- Not done: the receiver path (the DJ child node also carries mouse input,
  and the mouse can sleep or leave range).
